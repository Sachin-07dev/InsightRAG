# Text-to-SQL and the constrained-plan alternative

Full Text-to-SQL often gives a model table/column descriptions, asks it to link language to schema, generates SQL, parses an abstract syntax tree (AST), validates identifiers/functions/joins, and executes under a database policy. Neither a prompt nor an AST parser alone proves safety: a syntactically read-only query can still leak unauthorized rows, cross-join enormous tables, call dangerous functions or compute the wrong metric.

[Phase 6 planning](../../apps/api/src/insightrag/analytics/planning.py) is a rule-based subset: one known metric, one known breakdown and explicit period. [The service](../../apps/api/src/insightrag/analytics/service.py) compiles that typed plan to fixed SQL fragments; only data values are bound parameters. There is no model-generated SQL to validate and no general AST parser. SQL injection via `question`, `region` or `currency` therefore has no syntax channel. PostgreSQL permissions/RLS/timeout are independent enforcement layers. A multi-metric or vague period returns a clarification error instead of guessing.

If a model-assisted planner is added later, constrain its output to a Pydantic schema of metric IDs, dimension IDs, operators and literal values; validate the resolved plan against current dataset ACL and a versioned semantic catalog; compile server-owned SQL; compare with adversarial and golden calculation tests. Do not pass raw model SQL to a read-only account and call it safe. An AST parser would be appropriate for a reviewed SQL subset with function/join allowlists, cost limits and tenant predicates enforced by the database. A valid plan can still be semantically wrong, so human-reviewed examples and drift monitoring are necessary.
