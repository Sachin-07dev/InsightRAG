# Upload and progress communication

REST uses HTTP request/response semantics: the client sends authenticated `POST` raw bytes over HTTPS, receives a job ID, then polls an authenticated `GET` status endpoint. This fits a bounded upload and coarse progress. The [route](../../apps/api/src/insightrag/ingestion/routes.py) validates `Content-Length` and counts actual streamed bytes, since headers can be absent or false. A 50 MiB cap makes buffering explicit. For very large files, use short-lived, scope-limited multipart object-storage upload grants followed by server-side scan/commit; do not route a 2 GB file through this API process.

HTTP is an application-layer protocol; TCP and UDP are transport-layer protocols. Conventional HTTP/1.1 and HTTP/2 run over TCP; TLS protects bytes in transit. WebSocket begins with an HTTP upgrade handshake (or an HTTP/2 extended CONNECT) then supports full-duplex messages on a long-lived connection, typically over TCP/TLS. Server-Sent Events is one-way server-to-client HTTP streaming with browser reconnection support. Polling repeatedly opens ordinary HTTP requests; it is simple but costs request overhead and has update delay. HTTP/3 uses QUIC over UDP with its own encrypted, multiplexed transport; it is not “UDP without reliability.” TCP and UDP suit different protocols; neither is universally superior.

Progress changes only a few times per document, so polling avoids connection state, fan-out and reconnect authorization complexity. SSE may reduce request volume for many active watchers; WebSockets fit bidirectional live collaboration. At thousands of clients, measure polls per second, reverse-proxy timeouts, token expiry, stale connections and fan-out costs. Every progress read still authenticates and checks current upload permission; a WebSocket/SSE design would need periodic authorization refresh, reconnect cursor and server limits. S3 API calls from [storage](../../apps/api/src/insightrag/ingestion/storage.py) use HTTPS/TLS; PostgreSQL uses its wire protocol over TCP and Redis/Celery uses Redis protocol over TCP. Cloud TLS, private endpoint and residency controls remain deployment obligations.
