## Architecture, security, and data accuracy

The API in `analytics/routes.py` delegates to `service.py`; `planning.py` owns the finite metric grammar; `ingestion.py` validates the opt-in sales contract. Phase 4's scanned, versioned worker stages typed rows in the publication transaction. SQL expressions and dimensions are server constants, while IDs, dates, currency, and region are bound parameters. The API does not accept SQL, so UNION, CTE, comments, DDL, catalogue names, dangerous functions and unauthorized joins cannot become SQL syntax through the question field. That is a *code-path conclusion*, not a live hostile-input test. DuckDB uses an in-memory connection, parameterized row insertion, disabled external access and a 100,000-row/64MB setting; no API route exposes it. Those settings do not constitute an OS sandbox.

`service.py:analyze` checks a current resource query grant, reads only the active version under row RLS, uses a transaction-local timeout, rechecks policy revision and version, and audits the query. `0007_analytics.py` grants the shared runtime role SELECT and scoped INSERT; therefore the claim “dedicated read-only analytics credential” is **not** met. The Phase 6 RLS test previously covered Company A/B, Delhi-only access, full-region contribution and tombstoning. Workspace, forged-header, revocation and pool-context checks exist in the broader security integration suite, but were not rerun in this audit. There is no analytics response cache or external connector to test for leakage. No raw private query/result logging was found in the reviewed analytics module; broader telemetry settings were not re-audited.

**A — Previous three complete months:** `plan_question` forms `[first day three months ago, first day this month)` from `datetime.now(ZoneInfo(org.reporting_timezone))`; the unit test checks a year crossing. Completeness of underlying source feeds is unknown. **B — Contribution:** numerator and denominator share dataset version, currency and period; `has_complete_sales_scope` denies a denominator if any active region lacks entitlement. The prior RLS test checks 100.10 / 300.30 = 33.33% after access is granted. **C — YoY:** additive metrics use `(current-prior)*100/prior`, null for absent/zero prior; negative prior is mathematically processed but lacks approved interpretation. MoM is missing. **D — Margin:** SQL computes `(SUM(revenue)-SUM(cost))*100/SUM(revenue)`, null at zero total revenue, avoiding average-of-row-ratios; no independent executed SQL oracle was recorded. **E — Joins:** the query has no joins to detail tables, so this implementation cannot fan out sales; requested one-to-many join behavior is unsupported and untested. **F — FX/refunds:** negative signed revenue/cost and decimal arithmetic are supported; exchange rates, conversion dates and provenance are absent. A `returns` column counts units, not refunded currency. These are declared assumptions, not approved financial policy.

## Performance, API, documentation and interview readiness

There is no measured SQL p50/p95, ingestion throughput, connection-pool saturation, DuckDB peak memory, or concurrency capacity. The scope/date index in `0007_analytics.py` is plausible for constrained predicates; index benefit is **not verified**. Per-row worker inserts and in-memory parse/snapshot bounds constrain large files. The API returns decimal strings, units, filters, timezone, half-open periods and dataset version; unsupported/ambiguous input generally becomes a structured 422. Database outages/timeouts were not exercised through the API in this audit. No LLM explanation is invoked, so model rewriting of numeric output is currently impossible by this route.

The [module guide](README.md), [architecture](architecture.md), [walkthrough](implementation-walkthrough.md), [comparisons](technology-comparisons.md), [security](../../security/analytics-security.md), [tests](../../testing/analytics-tests.md), [learning journal](../../learning-journal.md), and [25-question interview bank](../../interview/phase-06-analytics.md) are substantive and generally candid about boundaries. They cover OLTP/OLAP, DuckDB/PostgreSQL, modelling, metric semantics, SQL safety, formulas and debugging. Their AST, window-function, FX and connector discussions describe deferred choices, not implemented code. A reviewer should not present those topics as production capabilities. The interview bank has short/deep answers, project examples, two answered follow-ups, alternatives and common mistakes; worked independent query plans and real performance results remain missing.
