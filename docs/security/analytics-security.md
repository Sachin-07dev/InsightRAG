# Analytics authorization and threat model

The API validates OIDC identity and current organization membership through the existing [security dependency](../../apps/api/src/insightrag/security/dependencies.py). A client-supplied organization header or valid JWT alone does not grant dataset access. [The service](../../apps/api/src/insightrag/analytics/service.py) requests analytics purpose, checks `can_resource(...,'query')`, verifies dataset kind/active state and reads only the active version. SQL has bound values and allowlisted fragments. [The typed table RLS](../../apps/api/migrations/versions/0008_analytics_scope.py) requires a transaction-local, server-set `app.analytics_resource_id` matching each row. It evaluates the current resource query grant as a scalar subquery, then intersects current-user region entitlements and the active version. Missing scope returns no rows. Context, grant and RLS checks still occur in PostgreSQL; setting a resource ID by itself never grants access. Transaction-local user/org/purpose/resource context prevents pooled-connection bleed.

The complete-scope boolean is a security-definer database function. It must be audited carefully: it returns only true/false, checks current query permission and active-version rows, and denies national share if *any* active row lacks a region entitlement. It never returns unauthorized region names. This avoids the common failure of dividing Delhi by only the regions visible to a partially entitled user while labelling the result “national.” The runtime role cannot update/delete typed rows. A 3-second timeout, 8 MiB work memory, 500-group cap and existing API rate limits reduce abuse; they do not replace per-tenant concurrency budgets or PostgreSQL `temp_file_limit`/CPU controls.

Deletion tombstones the resource immediately, so `can_resource` and RLS stop reads even before physical cleanup. The typed table cascades when source versions are physically deleted. The service locks/checks policy revision and rechecks active version in the response transaction. A snapshot exported to DuckDB would need the same authorization/version fencing, encrypted isolated storage, retention and purge propagation; [the current local adapter](../../apps/api/src/insightrag/analytics/local.py) has no production snapshot path. Prompt injection cannot execute SQL here because document/model content is never interpreted as instructions or SQL syntax. The scoped policy passed targeted real-PostgreSQL checks and the full 62-test integration suite; an independent security assessment is still required. Row-entitlement administration, FX policy, source connector credentials and independent audit export need review.

The DuckDB adapter's 64 MiB engine memory setting is **not** a hard process-memory boundary. Do not send private production data to it until process/container isolation and authorized snapshot lifecycle are implemented and tested.
