# Dimensional modeling in the Phase 6 sales slice

**What and why.** A fact table records business events at a declared grain; dimensions describe how to group/filter them. [The typed sales table](../modules/analytics/implementation-walkthrough.md) uses one transaction ID per row and version. `region`, `product`, `transaction_date`, and `currency` are dimensions. Revenue, cost, units and returns are additive measures over compatible groups. The grain matters: joining a transaction to multiple product tags before summing would count it repeatedly.

**How and where.** [The validator](../../apps/api/src/insightrag/analytics/ingestion.py) rejects duplicate transaction IDs and [the migration](../../apps/api/migrations/versions/0007_analytics.py) adds a unique key. There are no joins in [the query compiler](../../apps/api/src/insightrag/analytics/service.py); approved grouping is total, region, product or month. This is a single fact table, not a star schema yet. A star would add product/date/region dimension tables with many-to-one fact relationships; a snowflake would normalize those dimensions further. An unrestricted many-to-many tag join would require preaggregation or an explicit allocation rule.

**Production and improvement.** Synthetic transaction IDs are only unique within a version. Real source systems need stable event identity, correction semantics and late-arriving data policy. Repartition by date or tenant only after EXPLAIN and load tests show benefit. Add dimensions and foreign keys after product/region catalogs and slowly changing dimension rules are approved. Interview defense: define the grain before designing joins; compute aggregates from the fact once, then join one-to-one summaries or dimension keys, never duplicate fact rows accidentally.
