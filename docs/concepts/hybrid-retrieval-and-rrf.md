# Hybrid retrieval and reciprocal rank fusion

Dense retrieval finds semantic paraphrases; sparse retrieval finds rare literal terms. `retrieval/service.py` runs both over the same authorized active-version scope and `retrieval/ranking.py` deduplicates by `(resource_id,version_id,position)`. A chunk appearing in both channels is counted once but receives two rank contributions. The stable key prevents a new document version from being mistaken for the old chunk.

RRF assigns `score(d)=Σ_channel 1/(k+rank_channel(d))`; this project uses `k=60`. Suppose A ranks dense #1 and sparse #3: `1/61+1/63≈0.03227`. B ranks dense #2 and sparse #1: `1/62+1/61≈0.03252`, so B wins. A missing channel contributes zero. The constant dampens a single #1 advantage; weighted RRF could multiply each channel contribution, but weights require held-out labels. Deterministic ties sort by resource/version/position. RRF uses ordinal positions, avoiding a false comparison between cosine **distance** and PostgreSQL lexical **rank**.

Dense-only is cheaper when lexical identifiers are unimportant; sparse-only is cheaper when exact terminology dominates; hybrid can improve coverage but also adds latency and noise. A cross-encoder or authorized API reranker can reorder the bounded fused pool at further latency/cost. `scripts/evaluate-retrieval.py` reports an actual tiny synthetic ranking exercise only; it cannot establish production lift. A real decision needs labelled queries, relevance grades, fixed corpus and model versions, permission-aware splits, and paired MRR/NDCG/Recall plus p95 latency. Watch disagreement: one channel may surface a correct identifier while another returns a semantic but wrong policy. Fusion does not validate truth; citation and answer evaluation follow.
