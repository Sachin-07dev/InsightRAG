# Context window and token budget

An LLM has a finite context window shared by system instructions, prior conversation, retrieved evidence and generated output. Prompt tokens are input; completion tokens are output. `retrieval/context.py` uses Phase 4's pinned `cl100k_base` tokenizer to cap **evidence** at 2,400 tokens by default and limits included chunks to six. This is an estimate for a provider with a different tokenizer; reserve system, history and completion headroom separately in deployment configuration. The current adapter does not know the actual model's advertised context limit, so a provider may still reject an oversized request. That is a documented limit.

The builder deduplicates identical text within a source version, keeps document title/version/locator beside the excerpt, and uses deterministic fused/reranked order. It truncates only the last fitting excerpt, never invents a page. If a token boundary decodes to text not contained in the source, citation verification fails rather than fabricating evidence. Lost-in-the-middle describes a model's reduced use of evidence placed deep in long context; piling on K can worsen answer quality and cost. More advanced parent-child retrieval could fetch an enclosing section after chunk ranking, but requires parent provenance and more tokens. Extractive compression preserves exact source spans; generative compression may distort facts and needs its own verification. Diagnostic selection traces should include IDs, ranks and exclusion reasons, never raw private text in ordinary logs.

Example: a 4,000-token model window with 500 instruction tokens, 300 history tokens and 800 reserved output tokens leaves at most 2,400 for evidence. If two 1,000-token chunks plus headers fit, a third 1,000-token chunk cannot be included whole. The configured budget is evidence-only and does not by itself prove the provider's full-window constraint.
