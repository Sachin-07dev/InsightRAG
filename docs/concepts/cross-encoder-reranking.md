# Cross-encoder and API reranking

A bi-encoder independently embeds query and chunk, enabling reusable vector indexes. A cross-encoder jointly processes query and candidate text with transformer attention; token interactions can detect fine-grained relevance, but scoring every chunk costs roughly one model inference per pair. Use it after a bounded candidate stage. Attention computes query/key/value interactions over tokens; this can discriminate “Delhi 2025” from a semantically similar “Mumbai 2024” chunk that a vector search might rank highly.

The project implements an **optional HTTPS score adapter** in `retrieval/rerank.py`, not a bundled local cross-encoder. It sends at most `retrieval_rerank_k` authorized texts, expects one finite score per input, and sorts descending with deterministic ties. `retrieval/service.py` catches a reranker outage and falls back to fused order; embedding or generation failures instead fail the query. Scores are meaningful only within that reranker request and cannot be compared with cosine distance. A real provider requires a privacy/residency assessment, model/version pinning and latency/cost measurement; the adapter's `{scores:[...]}` JSON is a project contract, not a universal API.

Alternatives include local CPU cross-encoder (lower egress, higher latency), GPU batching (throughput but operational cost), or no reranker (simpler, faster). Select on paired NDCG/MRR and answer faithfulness alongside p95, provider cost and tenant isolation. Test that unauthorized candidates never reach the adapter. Under heavy load, bound concurrent batches, apply timeout and backpressure; do not let retries amplify provider 429s.
