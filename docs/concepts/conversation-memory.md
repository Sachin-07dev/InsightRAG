# Conversation memory and permission revalidation

HTTP requests are stateless at the transport layer; `rag_conversations` and `rag_turns` in migration `0006_retrieval.py` add explicit server persistence. RLS restricts a conversation to the current owner, organization and workspace membership. Turns store the question, outcome and opaque source/version references, **not generated answer text or document excerpts**; this reduces residual copied content after source deletion. `retrieval/service.py` reads only the last **question** for short pronoun follow-ups, appending rather than replacing current constraints. Old answers and chunks are never inserted into a new prompt simply because they appeared in history. Every turn performs fresh retrieval and current ACL/version checks. A valid conversation ID from another tenant or user yields 404.

This protects against stale evidence and permission revocation, but is not full conversational understanding. “What about Mumbai?” without an explicit pronoun may need a carefully evaluated rewrite; an LLM rewrite could drop Delhi, date or unit constraints and cause query drift. Summarized long-term memory can be poisoned by prior user or document text, so any future summary should be scoped, versioned, limited and treated as untrusted. Conversation retention and deletion policies are not yet implemented; deployment must set and enforce tenant-specific retention before production use.

For a permission change between turns, the next query uses the current membership/grants and only current active documents. A stored historical citation is not a capability to open the source. Workspace scope is fixed when the conversation is created; the request must match it on every continuation. During inference, the service rechecks the evidence and policy before persisting or returning an answer.
