# Code walkthrough and operational behavior

`DashboardRequest` accepts only scope and questions, never rows or ECharts options. `dashboard` reuses the Phase 7 `query` route, which reuses Phase 6 `analyze`. A denied or unavailable card raises and prevents a partial dashboard from being returned. Each result is turned into a `ViewSpecification` by `build_view`: the function validates nonempty and at most 500 rows; checks labels are unique and each non-null decimal is finite; infers monthly line versus single-row KPI versus categorical bar; rejects a requested line without monthly labels and multi-series/geographic forms without a governed data contract. Values retain their original decimal strings and `source_rows`.

The frontend maps strings to JavaScript numbers only for plotting. A numeric SVG coordinate is necessarily approximate for some high-precision values, so the visible HTML table remains authoritative. `ResizeObserver` updates plot size; chart teardown disposes its instance to prevent leaks on refresh. Tooltips and zoom are local presentation interactions. Changing year or region triggers a new authorized request, never a client-side SQL calculation. The proxy forwards the token and org ID without persistence and adds `no-store`.

Failure examples: an expired token returns 401; inaccessible dataset or workspace returns 404 from trusted services; unsupported MoM/category intent returns 422; a changed dataset version during multi-card execution returns 409; malformed numeric values or duplicate labels return 422. The dashboard has a 25-second wall-clock cap; it cancels remaining work and returns 504 before the web proxy's 30-second deadline. These errors are shown as non-sensitive status messages in the UI. Six sequential LangGraph/SQL calls can still approach that cap; this is a known scaling limit, not a benchmark. A future batch analytics API with snapshot consistency and bounded parallelism should be measured before introduction.
