# Phase 5 retrieval security invariants

**Identity to evidence.** The bearer token is verified by the existing OIDC verifier. `X-Organization-ID` selects a claimed scope, then the server looks up the issuer/subject and current organization membership. A valid JWT and header alone do not establish workspace membership or document permission. `retrieval/repository.py` requires current workspace membership, explicit document read grants when IDs are supplied, and SQL-side tenant/workspace/active-version/model/`can_resource` constraints in both dense and FTS branches. Phase 4 `ingestion_chunks` RLS independently permits only authorized active chunks. No candidate text should reach fusion, a reranker or the LLM before these checks. A dataset resource cannot enter document RAG.

**After inference.** Model calls can take seconds. `retrieval/service.py` reopens a tenant-scoped transaction, rereads the exact candidate text through current access and active-version predicates, locks/checks organization policy revision, writes the owner-scoped turn and audit event, and returns. A changed grant, deleted document or superseded version fails with 409. A valid source label is necessary but does not prove semantic entailment. The client must not treat the citation label as an access token. Source download and historical citation resolution would need independent authorization; this phase does not expose them.

**Conversation and cache.** Migration `0006_retrieval.py` adds RLS on conversation and turn tables; only the owner in a current workspace can read/write them. Turns retain questions, outcomes and opaque source references but no generated answer or source excerpt. The service uses prior questions, not prior evidence, to resolve follow-ups. The current answer path has no shared cache. A future cache must key by tenant, user/grants or policy revision, workspace, model, document-version set and query profile, then invalidate on grant/version/deletion change. Cache hits must still reauthorize before release.

**Prompt injection and egress.** Documents and model output are untrusted. The model receives only authorized chunks as data under a system instruction; it has no SQL/Python or network tool execution. Pydantic validates bounded JSON, source labels are checked, and provider failures fail closed. This is defense in depth, not a guarantee that a model cannot be persuaded to write unsupported text. External embedding/reranking/generation services need approved egress, contractual residency, encryption in transit, logging controls and data-processing review. The chat adapter requests `store=false` where supported; that parameter does not replace a provider-specific retention agreement. HTTPS-only endpoints in configuration are necessary but insufficient; DNS/egress allowlists and certificate enforcement belong to deployment. The default application log records counts, status and duration, not query or chunk text.

**Tests and residual risks.** Real PostgreSQL tests in `test_rls_integration.py` prove cross-tenant candidate exclusion, denied explicit document scope, deleted-document exclusion, owner-scoped conversation continuation and actual cited versions on a synthetic fixture. Unit tests verify forged labels fail. They do not prove all prompt-injection attacks, semantic citation support, data residency, KMS controls, conversation retention or no race after final transaction commit. A 404 masks inaccessible resource existence; 409 signals changed authorization/evidence; 502 rejects invalid labels; 503 represents provider failure. Audit and monitoring must alert on repeated denial or citation-validation failures without storing private content.
